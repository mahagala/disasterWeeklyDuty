## 三、實際落地的修改

### A. 效能與韌性修正(`app.js`)

1. **搜尋框 debounce(250ms)**
   - 問題:`table-search` 的 `input` 事件直接綁 `filterAndDisplayData`,每按一鍵就重跑「過濾 + 排序 + 地圖重繪 + 建表」。
   - 修正:新增 `debounce()` 工具,搜尋改為 `debounce(filterAndDisplayData, 250)`。

2. **`translateCountry` 加入 memoization**
   - 問題:每次呼叫都對整張 `COUNTRY_MAP` 迴圈建立 `new RegExp` 做模糊比對,而它在渲染每一列時被反覆呼叫。
   - 修正:以原始字串為鍵的 `Map` 快取(`_translateCountryCache`);計算邏輯拆到 `translateCountryRaw()`。

3. **排序/分類一致化**
   - 問題:篩選用 `getStandardCategoryGroup(d.type)`(正規化群組),排序用 `CATEGORY_PRIORITY[d.type]`(原始字串)。經驗證目前資料下兩者剛好一致,故屬**防禦性重構**而非活 bug。
   - 修正:新增 `GROUP_PRIORITY` 與 `getCategoryPriority()`,排序改以標準群組為唯一真相來源,杜絕未來新增類別時忘了同步優先級表。

4. **`getCategoryInfo` 大小寫不敏感**
   - 問題:`CATEGORY_MAP` 為精確大小寫查表,`earthquake`/`EARTHQUAKE` 等會被誤落「其它災害」(篩選與排序會一起錯)。
   - 修正:由 `CATEGORY_MAP` 建立小寫正規化查表 `CATEGORY_MAP_LOOKUP`,查詢前 `trim().toLowerCase()`。已驗證所有 key 小寫後無碰撞。

### B. 定時快照機制(新功能)

**目的**:純靜態頁面「沒開著就不存在」,無法在背景自行抓資料。改由伺服器端定時抓取、產生快照檔,讓頁面**打開即讀、秒開、且完全避開瀏覽器 CORS**。

- **`.github/workflows/update-data.yml`**:每小時排程(`cron: 0 * * * *`)+ 手動觸發;`permissions: contents: write`;有變更才 commit `data.json`。
- **`.github/scripts/fetch-feeds.mjs`**:Node 20 腳本(無相依套件,用內建全域 `fetch`),抓取 7 個 feed,存為 `data.json`。含重試/逾時;**全部失敗則不覆寫既有快照**。
- **`app.js`**:
  - 開頁改為 `loadFromSnapshot()` 優先;失敗才退回 `loadData()` 即時抓取(**完全相容**)。
  - `data.json` 儲存各來源**原始文字**,沿用既有 4 個 parser(`parseGdacsRSS`/`parseErccRSS`/`parseUsgsAtom`/`parseReliefWebAPI`),**未重寫任何解析邏輯**。
  - 去重 + 台灣修正抽為共用的 `dedupeAndCorrectDisasters()`。
  - 新增「📅 資料時間」指示器(`setSnapshotTimeIndicator()`);「立即同步」按鈕仍走即時抓取並隱藏該指示器。
- **`index.html`**:header 的 `.source-statuses` 內新增 `#snapshot-time` 元素。

**資料流**

```
GitHub Actions(每小時) → fetch-feeds.mjs 抓 7 來源 → data.json commit 回 repo
                                                              │
使用者打開頁面 → loadFromSnapshot() 讀 data.json ──成功──→ 秒開、顯示「資料時間」
                                    └──失敗/不存在──→ loadData() 即時抓取(原行為)
```

## 五、合併後的啟用步驟(重要)

1. **Settings → Actions → General → Workflow permissions** 設為 **Read and write permissions**(否則排程無法把 `data.json` 推回 repo)。
2. **Actions** 分頁 → 「定時更新災害資料快照」→ **Run workflow** 手動跑第一次,產生第一份 `data.json`。
3. 若 GitHub Pages 由 `main` 分支部署,commit `data.json` 會自動觸發重新部署。

## 六、已知取捨與後續可考慮項目

- **每小時 ≈ 24 次 commit/天**:嫌吵可將 cron 改為 `0 */6 * * *`(每 6 小時)。
- **GDACS 的 Cloudflare**:GitHub 伺服器端通常不被 Origin 阻擋,但不保證;失敗時該來源標記失敗,使用者仍可按「立即同步」。
- **`file://` 雙擊**:瀏覽器多半禁止 `file://` 用 `fetch` 讀本地檔,故快照好處**主要在 GitHub Pages(https) 版本**;雙擊本機開啟會自動退回即時抓取。
- **尚未採納(需先破除零建置限制)**:單元測試框架、模組化拆分、i18n、PWA。
